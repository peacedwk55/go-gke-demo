ผมจึง commit ไว้แต่ไม่ apply แล้วรอไปทำกับคลัสเตอร์ใหม่ — การตัดสินใจนี้ต้องรู้ว่า ตอนนี้มีอะไรกำลังรันอยู่ที่เสียไม่ได้ ซึ่งเครื่องไม่รู้ plan มีค่าตรงที่บอกล่วงหน้า แต่มีค่าต่อเมื่อมีคนอ่าน

ทำไมประตูมนุษย์อยู่เส้นเดียว

คำตอบไม่ใช่ "เส้นแอปสำคัญน้อยกว่า" — คือ ราคาของการแก้กลับ ต่างกันหลายเท่า

สิ่งที่ CI ทำไม่ได้เลย

คำถามว่า "มี secure approve ไหม" มีอีกครึ่งคำตอบที่ไม่ใช่เรื่องการอนุมัติ — คือขอบเขตที่ CI เอื้อมไม่ถึงตั้งแต่ต้น

CI ไม่มี credential ของคลัสเตอร์แม้แต่ตัวเดียว สิ่งเดียวที่มันเขียนออกไปข้างนอกคือ commit ใน Git — ArgoCD ที่อยู่ข้างในคลัสเตอร์เป็นคนไปดึงเอง เรียกว่า pull-based เพราะทิศทางกลับกับที่คนคุ้นเคย

ผลตรง ๆ คือ ถ้า CI ถูกยึด คนที่ยึดได้แค่สิทธิ์ commit ไม่ได้สิทธิ์สั่งคลัสเตอร์ และ invariant 3 จะทำให้ build ล้มถ้ามีคำว่า kubectl โผล่ที่ไหนก็ตามใน .github/workflows/

ฝั่ง infra ก็มีขอบเขตเดียวกัน — identity ที่ CI สวมตอน plan ไม่มีสิทธิ์ apply เลย มันบรรยายได้ว่าอะไรจะเปลี่ยน แต่เปลี่ยนไม่ได้ และ OIDC provider ผูกไว้กับ repo เดียวด้วย attribute.repository — repo อื่นถือ token ที่ถูกต้องก็ใช้ไม่ได้
